# 다국어 기반 성형외과 웹사이트 리뉴얼

> **복잡한 의료 정보를 여러 언어로 일관되게 제공하고, 모션 디자인을 탐색 경험으로 연결한 Next.js 웹 프로젝트**

![Next.js](https://img.shields.io/badge/Next.js-16-black?logo=nextdotjs) ![TypeScript](https://img.shields.io/badge/TypeScript-React-3178C6?logo=typescript&logoColor=white) ![GSAP](https://img.shields.io/badge/GSAP-ScrollTrigger-88CE02) ![i18n](https://img.shields.io/badge/i18n-5_locales-486581)

> **익명화 안내:** 포트폴리오 공개를 위해 실제 병원명·브랜드명·고객 정보는 문서에서 제외했습니다. 스크린샷·코드·배포 링크의 상표·개인정보·비밀정보는 공개 전 별도로 점검해야 합니다. 본 문서는 대화와 공유된 코드·오류 기록을 바탕으로 정리한 개발 기록이며, 미확인 기능의 운영 검증을 주장하지 않습니다.

## 02. 핵심 기여와 기술 선택

### A. next-intl — 5개 언어와 CMS 번역 경계

- `next-intl`을 이용해 UI 문구의 번역 리소스를 분리하고 locale 기반 렌더링을 구성했습니다.
- 언어 전환 시 문구가 갱신되지 않는 문제, `next-intl` 설정 파일 탐지 오류, 공통 레이아웃·푸터·VLOG·안전 정보·카테고리 등 번역 누락을 추적했습니다.
- 관리자에서 입력한 콘텐츠는 **정적 메시지 번역**만으로 해결되지 않으므로, 콘텐츠 소스 유형과 번역 데이터의 저장 구조·조회 경로까지 검토했습니다.
- Oracle의 컬럼 식별자 및 `CK_CMS_I18N_TYPE` 제약조건 오류를 통해 **프론트의 새 콘텐츠 유형이 DB 스키마에도 반영돼야 한다는 점**을 경험했습니다.

[자세히: i18n 설계 및 검증](docs/01-I18N-ENGINEERING.md)

### B. GSAP / ScrollTrigger — 연출과 라이프사이클

- 브랜드 Intro, Hero 시각 효과, 섹션별 등장, 스크롤 기반 고정(`pin`) 및 전환 인터랙션을 구성했습니다.
- `useRef`로 애니메이션 대상 DOM을 참조하고, `useEffect` 또는 적절한 레이아웃 이펙트와 GSAP 컨텍스트/타임라인을 통해 시작·종료 시점을 관리했습니다.
- `pin-spacer` 생성과 React 언마운트가 충돌할 수 있는 문제, Intro의 새로고침 감지로 인한 화면 깜빡임을 분석했습니다.
- Intro 재생 조건은 서버 요청 헤더 기반 판단이 **정적 배포에서 불가능**해져, 브라우저 내비게이션 신호로 변경하면서 생기는 제약도 검토했습니다.

[자세히: 인터랙션 구현과 트레이드오프](docs/02-GSAP-UIUX.md)

### C. 프론트와 운영 데이터를 연결한 웹 아키텍처

- 카테고리/상세, 콘텐츠, 상담·예약, 계정 및 관리자 화면의 역할을 분리했습니다.
- API 데이터가 `null`이거나 인증되지 않은 사용자가 접근하는 경우, 화면이 중단되지 않도록 예외 처리를 검토했습니다.
- 발표용 정적 데모와 동적 백엔드가 결합된 실제 서비스는 **서로 다른 기능 범위**임을 명확히 구분했습니다.

[아키텍처·데이터 흐름](docs/03-ARCHITECTURE.md) · [기능 및 요구사항 명세](docs/04-REQUIREMENTS.md)

## 04. UI/UX 설계 기준

1. **시각적 위계:** 큰 타이포그래피, 이미지, 간격으로 정보의 우선순위를 안내합니다.
2. **연출의 목적성:** Intro/GSAP 애니메이션은 브랜드 인지와 섹션 흐름을 지원하되 메인 탐색을 방해하지 않도록 종료·Skip을 고려합니다.
3. **일관성:** 모바일/데스크톱의 동일한 콘텐츠 의미를 유지하면서 레이아웃을 변경합니다.
4. **언어 확장성:** 번역 문장 길이가 다른 언어에서도 버튼·메뉴·푸터 레이아웃이 깨지지 않도록 고려합니다.
5. **접근성/성능:** `prefers-reduced-motion`, 버튼 포커스, 이미지 레이아웃 안정성, 필요한 시점의 지도 SDK 로딩 등을 검토합니다.

## 05. 트러블슈팅 — 이 프로젝트의 핵심 기술 기록

문제 해결을 단순 오류 목록이 아니라 **관찰 → 가설 → 원인 → 조치 → 확인 수준 → 회고**로 정리했습니다. 확인된 원인과 추정 원인을 구별하고, 해결 결과가 확인되지 않은 항목은 그대로 표시했습니다.

| 주제 | 대표 이슈 | 기술적 핵심 |
| --- | --- | --- |
| i18n | `next-intl` config 누락 / 언어 변경 미반영 | 서버·클라이언트 번역 컨텍스트와 라우팅 |
| i18n + DB | `ORA-00904`, `ORA-02290` | Oracle 식별자·체크 제약조건·콘텐츠 타입 동기화 |
| GSAP | `removeChild`/`pin-spacer` | React가 관리하는 DOM과 외부 라이브러리의 DOM 변형 |
| GSAP + 정적 배포 | Intro 깜빡임/미재생 | SSR 초기 마크업, 하이드레이션 이후 effect, Navigation Timing |
| 이미지/성능 | `next/image fill` 경고 | 포지셔닝 컨텍스트·LCP |
| 인증/레이아웃 | 헤더·푸터 사라짐, 로그인 모달 미복귀 | 불리언 조건식, 모달 전역 상태, 라우팅 |
| 예약/DB | `ORA-00942`, `ORA-00955`, `ORA-00001` | 엔티티 테이블 매핑, DDL 멱등성, 유니크 제약 |
| 정적 배포 | Next RSC `.txt` 경로, 동적 API 부재 | 정적 export와 서버 렌더링의 경계 |

## 06. 기술적 의사결정

| 결정 | 이유 | 배운 점 |
| --- | --- | --- |
| 정적 UI와 동적 CMS 콘텐츠 번역 분리 | UI 문구와 운영 콘텐츠의 변경 주기가 다름 | 국제화는 화면뿐 아니라 저장 모델의 문제 |
| GSAP 타임라인과 DOM ref 사용 | 복수 요소의 진입/종료 순서를 세밀하게 제어 | 직접 DOM 조작 라이브러리는 React 수명 주기와 정리 계약이 중요 |
| 지도 SDK 지연 로딩 | 초기 화면에서 사용하지 않는 스크립트 비용을 미룸 | 성능 최적화와 초기화 타이밍 검증을 함께 수행 |
| 발표용 정적 배포와 동적 서버 기능 구분 | Cafe24 정적 환경에서 SSR/DB 기능을 직접 실행할 수 없음 | 배포 아키텍처의 제약을 사전에 식별해야 함 |
| 실패·미확인을 문서에 남김 | 성공 사례만 기록하면 원인 분석이 과장됨 | 재현 가능한 엔지니어링 기록이 면접 설명에 유리 |

## 07. 로컬 실행

```bash
# frontend 폴더에서
npm install
npm run dev
```

백엔드와 OracleDB는 별도 환경 변수·DB 설정이 필요합니다. 실제 `package.json`, `.env.example`, API 경로 및 DB 초기화 스크립트는 저장소 공개 전 프로젝트 상태에 맞춰 검증해야 합니다. **실제 계정·비밀번호·OAuth 비밀키·DB 접속 정보는 커밋하지 않습니다.**

## 09. 프로젝트를 통해 얻은 경험

**첫째, 국제화는 번역 문자열 교체 이상의 아키텍처 문제라는 것을 배웠습니다.** `next-intl`을 이용한 locale·메시지 관리뿐 아니라 관리자 콘텐츠를 저장하는 테이블과 DB 제약조건까지 연결되는 문제를 다루면서 프론트와 백엔드 사이의 계약이 중요하다는 점을 체감했습니다.

**둘째, 애니메이션은 잘 보이게 만드는 것만큼 안전하게 종료하는 것이 중요했습니다.** GSAP과 ScrollTrigger는 높은 표현력을 제공하지만 React의 컴포넌트 마운트·언마운트, 스크롤 복원, 동적 DOM, Skip 동작과 충돌할 수 있습니다. 이 경험을 통해 effect cleanup과 UI 상태 동기화를 더 엄격하게 보게 됐습니다.

**셋째, 오류를 한 계층에서만 보지 않게 됐습니다.** 화면에서 보이는 문제가 실제로는 Oracle 식별자, Next.js 라우팅, HTTP 인증 상태, 서버 렌더링·정적 export 차이에서 시작할 수 있다는 점을 경험했습니다.

**넷째, 배포 가능한 화면과 실제 운영 가능한 서비스는 다르다는 것을 배웠습니다.** 정적 발표용 페이지는 UI·인터랙션을 검증하기에 유용하지만 서버 API와 인증·DB 흐름까지 검증했다고 말할 수는 없습니다. 이를 명확히 구분하는 습관을 얻었습니다.

**다섯째, 문제의 재현 조건과 검증 상태를 설명하는 습관을 키웠습니다.** 발생한 오류의 문구·경로·영향 범위를 기록하고, 해결된 문제와 검증 중인 문제를 나누어 관리했습니다. 앞으로도 기능 구현만큼 디버깅 과정의 기록과 재현 가능성을 중요하게 다루고자 합니다.
