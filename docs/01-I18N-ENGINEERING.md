# next-intl 중심 국제화(i18n) 설계

> 면접에서 가장 강조할 기술 영역: **5개 언어 지원과 CMS 데이터 번역의 연결**

## 1. 목표와 범위

일반 사용자 화면과 관리자 관리 콘텐츠를 한국어, 영어, 일본어, 중국어 간체, 중국어 번체로 확장하는 프로젝트입니다. 언어 코드 예시는 `ko`, `en`, `ja`, `zh-CN`, `zh-TW`이며, 실제 저장소의 locale 키와 URL 표현은 설정 파일을 기준으로 확인해야 합니다.

**국제화(i18n)**는 여러 언어를 지원할 수 있게 코드/데이터 구조를 만드는 작업이고, **현지화(l10n)**는 언어별 문구·표현을 적용하는 작업입니다. 이 프로젝트에서는 UI 번역과 DB 기반 콘텐츠 번역을 구분했습니다.

## 2. 번역 데이터의 두 계층

| 계층 | 예시 | 권장 소유권 | 변경 흐름 |
| --- | --- | --- | --- |
| UI 고정 문구 | 내비게이션, 버튼, 모달, 지도 서비스 이름, 검증 메시지 | `next-intl` 메시지 리소스 | 개발 변경 → 번역 QA → 빌드 |
| 운영 콘텐츠 | VLOG/SAFETY/FOOTER, 메인 비주얼, 카테고리, 내비게이션 설정 | CMS/DB 번역 레코드 | 관리자 작성 → API → DB → 언어별 조회 |

한 화면에서 두 계층이 동시에 사용될 수 있습니다. 예를 들어 Footer의 `Contact` 제목은 메시지 리소스, 운영자가 수정하는 전화번호·병원 소개글은 API 기반 설정입니다. 언어 변경을 했는데 일부 영역만 한국어로 남으면 **해당 문자열이 어느 계층에 속하는지 먼저 확인**해야 합니다.

## 3. 프론트엔드 처리 흐름

```text
사용자 언어 선택
  ↓
locale 판별/유효성 확인
  ↓
URL 또는 i18n 컨텍스트 갱신
  ↓
next-intl 메시지 로딩
  ↓
useTranslations(namespace) 적용
  ↓
CMS 콘텐츠가 있다면 locale을 전달해 번역 조회
  ↓
레이아웃/줄바꿈/누락 키 검증
```

사용한 개념: `useLocale`, `useTranslations`, 서버 측 `getLocale`, locale-aware 경로 생성 유틸리티. SSR과 정적 export의 동작 차이가 있어 실제 App Router 구성 파일은 배포 방식과 함께 관리해야 합니다.

```tsx
// 실제 구현 스타일을 단순화한 예시 (원본 파일의 완전한 복사본이 아님)
const t = useTranslations("SocialAuth");
const activeLocale = useLocale();
const locale = isAppLocale(activeLocale) ? activeLocale : defaultLocale;

return <button>{t("google")}</button>;
```

**왜 이런 구조인가?** 컴포넌트가 번역 문자열 자체를 소유하지 않고 키만 참조하면 디자인/기능 코드를 수정하지 않고 언어를 교체할 수 있습니다. 유효하지 않은 locale에는 명시적 기본값을 사용해 예측 가능한 렌더링을 도모합니다.

## 4. 실제 경험한 문제

### 4-1. `Couldn't find next-intl config file`

Next.js 16.3 App Router에서 `getLocale()` 호출 시 발생했습니다. `next-intl` 설정을 Next.js 플러그인 및 요청 구성과 연결하는 부분을 점검해 설정 오류를 해소했습니다. **학습 포인트:** 런타임에서 번역을 읽는 코드와 빌드 시 설정 발견 규칙이 함께 맞아야 합니다.

### 4-2. 언어 드롭다운 전환 후 텍스트가 바뀌지 않음

드롭다운의 상태만 변경하는 것과 **locale 컨텍스트 및 경로가 실제 갱신되는 것**은 다릅니다. 언어 선택 후 `useTranslations`가 읽는 메시지 문맥과 화면 렌더링 경로를 점검했습니다. 이후 사용자가 변경한 번역들이 적용되는 것을 확인했습니다.

### 4-3. CMS 번역 유형 추가 시 Oracle 체크 제약 위반

새 콘텐츠 유형을 프론트/서버 코드에 추가해도 DB의 `CK_CMS_I18N_TYPE` 허용 목록에 없으면 `ORA-02290`이 발생했습니다. FOOTER, MAIN_VISUAL, CATEGORY, NAV_SETTING 등 추가 유형을 반영해야 했습니다. 기존 허용값이 누락되지 않도록 제약조건 변경 시 전체 유형 집합을 고려했습니다. **학습 포인트:** 문자열 기반 enum은 DB에도 스키마 계약으로 존재합니다.

### 4-4. Footer 소스 조회 실패 — `ORA-00904`

`FOOTER_SETTINGS.NAME` 컬럼 참조와 실제 Oracle 테이블의 식별자 표현이 맞지 않아 조회 API가 500을 반환했습니다. 실제 컬럼 정의를 확인하고 따옴표로 생성된 소문자 식별자(`"id"`, `"name"`)를 SQL에서 정확하게 참조하도록 수정하는 방향으로 처리했습니다. **학습 포인트:** Oracle의 인용 식별자는 대소문자 구분 때문에 ORM/직접 SQL 혼용 시 주의가 필요합니다.

### 4-5. 번역 누락 범위 추적

Hero 설명, VLOG 본문·타이틀, Footer 정보, 병원 지도 버튼/서비스 이름, 커뮤니티 콘텐츠, 안전 정보 등에서 번역 적용 범위를 반복 확인했습니다. 일부 항목은 수정 요청·점검 기록만 있으므로 **전체 누락이 최종적으로 0건임을 보장하지 않습니다.**

## 5. 검증 전략 — 면접에서 설명할 품질 기준

- [ ] 다섯 언어 모두에서 헤더/푸터/메뉴/버튼/폼 메시지 확인
- [ ] 언어 전환 뒤 페이지 이동·새로고침 시 locale 지속 확인
- [ ] CMS 데이터가 없는 언어의 fallback 정책 명시
- [ ] 번역 키 누락 시 콘솔/화면 표시 점검
- [ ] 긴 영문과 중국어/일본어 줄바꿈·너비 확인
- [ ] 새 `ENTITY_TYPE`을 API DTO, 서버 처리, DB 제약에 동시에 반영
- [ ] 정적 발표본과 서버 실행 모드 각각에서 경로/locale 검증

## 6. 면접용 핵심 답변

> “i18n 작업에서 가장 크게 배운 점은 정적 UI 문구와 관리자 CMS 콘텐츠가 서로 다른 저장·배포 주기를 가진다는 것입니다. `next-intl`에서 locale을 바꿔도 DB 기반 콘텐츠는 따로 언어별 조회/스키마 지원이 필요했습니다. 실제로 Oracle 체크 제약조건과 컬럼 식별자 문제로 번역 API가 실패했고, 프론트→API→DB 전체 계약을 확인하며 대응했습니다.”

**주의:** 이 문서는 기술 경험을 구조화한 기록입니다. 구현하지 않은 fallback 자동화나 전 언어 자동화 테스트를 '완료'로 표현하지 않습니다.
