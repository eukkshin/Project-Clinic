# GitHub 공개 전 점검표

> 면접 목적의 공개 저장소는 **신뢰성과 재현 가능성**이 중요합니다. 완료된 기능과 구현 예정 기능을 섞지 않는 것이 가장 중요합니다.

## 1. 브랜드/개인정보 익명화

- [ ] `README.md`, `docs/`에서 실제 상호·브랜드명 제거
- [ ] `src/`, `public/`, 메타데이터, 이미지 파일명, 대체 텍스트, CSS 클래스, API 응답에 브랜드명 포함 여부 검색
- [ ] 병원 주소·전화번호·실제 고객/환자 정보, 의료 이미지 사용 권한 확인
- [ ] 실제 관리자 계정·비밀번호·토큰·OAuth 키·DB 접속 정보 공개 금지
- [ ] Git 전체 히스토리에 남은 비밀 정보 확인 (파일 삭제만으로 과거 커밋에서 사라지지 않음)
- [ ] 화면 스크린샷에 이름·전화번호·상담 내용 등 개인정보 없는지 확인

## 2. 실제 구현 근거

- [ ] README 기능 표의 현재 구현/미구현 상태 업데이트
- [ ] 가장 강조하는 i18n 코드 파일 2~3개와 GSAP 타임라인 2~3개 링크
- [ ] 각 트러블슈팅에 실제 수정 커밋/PR 링크 추가 가능하면 연결
- [ ] 오류 재현 및 해결 여부를 로컬에서 재확인
- [ ] 5개 언어 화면 캡처와 반응형 비교 이미지 추가
- [ ] Lighthouse/성능 수치가 없다면 개선 퍼센트·정량 성과를 임의 기재하지 않기
- [ ] 본인 기여 범위를 팀/개인 기준으로 명확히 표시

## 3. 소스 공개 안전성

- [ ] `.gitignore`에서 `.env*`, `node_modules`, `.next`, `out`, 인증서, 로그 파일 제외
- [ ] 공개 가능한 예시 설정만 `.env.example`로 별도 제공하고 값은 placeholder 사용
- [ ] 저장소에 실제 DB 덤프, 고객 정보, private 인증키 없음
- [ ] 라이선스·사진 저작권·사용한 로고 공개 허용 여부 확인
- [ ] API 예시에는 실제 내부 서버 주소나 인증 토큰이 들어 있지 않도록 확인

## 4. GitHub 추천 순서

1. 원본 프론트/백엔드에서 공개할 범위를 결정합니다.
2. 루트 `README.md`와 `docs/`를 복사합니다.
3. 최종 코드와 비교해 문서의 기능/검증 상태를 업데이트합니다.
4. 시크릿 스캔 후 `git status`, `git diff --cached`로 커밋 대상 확인합니다.
5. README 및 문서 커밋을 만듭니다. 예: `docs: add portfolio overview and engineering case studies`.
6. GitHub의 렌더링 링크/표/다이어그램을 확인합니다.

## 5. 스크린샷 추천

- ① 메인 Hero 데스크톱
- ② Intro/ScrollTrigger 연출 장면
- ③ 같은 페이지의 5개 언어 비교
- ④ 관리자 CMS 번역 입력 화면(더미 데이터만)
- ⑤ 모바일 레이아웃

스크린샷을 넣으려면 `docs/images/`에 사용 권한이 있는 이미지 파일을 저장하고 README에서 상대 경로로 연결합니다. 이 문서 묶음에는 실화면 스크린샷이 **포함되어 있지 않습니다.**
